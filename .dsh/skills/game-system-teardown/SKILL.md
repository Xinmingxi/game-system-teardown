# 游戏系统拆解

## 这个技能解决什么

用户在为**游戏系统策划求职**做作品积累。价值不在文档数量，在于每份拆解都**还原了设计决策**。

一份拆解只有满足这一点才算交付：读完能知道设计者当时在权衡什么。

## 开工前必读

工作区里的三份文件，依次读：

1. `00_规范/00_总览.md`——分类、命名、格式、会话流程
2. `00_规范/01_拆解架构.md`——四层结构、六个必答问题、循环图、参数还原、崩坏预演
3. `00_规范/02_拆解模板.md`——15 节填空模板

读不到就问用户库在哪。**不要凭记忆编造规范**——规范会变，记忆会旧。

## 八步工作流

### 第 1 步 · 定题

确认四件事：品类文件夹、游戏（官方简体中文名，去标点）、系统名（必须在词表内）、**游戏版本号**。

缺版本号就问，不要猜。系统会改，结论必须绑版本。

### 第 2 步 · 备料

向用户要三样。缺了照样能拆，但要在文档里标注「待补」：

- **体验节点**：第 1 小时 / 第 3 天 / 第 7 天 / 第 30 天分别发生了什么
- 截图或录屏要点
- 已知数值（官方公示、攻略、实测样本）

只问用户可能知道的。别问他要他没测过的数。

### 第 3 步 · 起草

复制 `02_拆解模板.md` 到对应品类目录，改名 `游戏名_系统名_拆解.md`，逐节填。

### 第 4 步 · 质量门槛（硬性）

全部满足才能交付：

- 第 1 节写出 2~3 个 MDA 美学感受，不是「好玩」
- 第 3 节有循环，且写明转一圈要多久
- 第 5 节参数 3~5 个，写**形状**不写精确值
- 第 10 节做了反事实推演
- 第 11 节写了崩坏预演，并指名一种死法
- 第 13 节有明确取舍（保留/砍/改）
- 全文「因为/所以」多于「是/有」
- 换个游戏名读不通

缺哪条补哪条；补不了就明说缺什么数据，**不要用套话填空**。

### 第 5 步 · 转 Word

在库根目录运行：

```
python 工具/md2docx.py 品类目录\文件名.md 品类目录\文件名.docx
```

转换后不要手改 docx——下次转换会覆盖。

### 第 6 步 · 登记

在 `00_规范/04_进度索引.md` 加一行：序号 / 游戏 / 品类 / 系统 / 状态 / Word / 一句话结论 / 日期。

一句话结论要写到未来的自己一眼看懂命门。

### 第 7 步 · 抽卡（2~4 张，不要更多）

| 类型 | 前缀 | 存哪 | 硬性要求 |
| --- | --- | --- | --- |
| 理论卡 | T- | 20_知识库/理论 | 只写本次真正用到的理论，不凑数 |
| 经验卡 | E- | 20_知识库/经验 | 标题是断言，且写出失效条件 |
| 反例卡 | C- | 20_知识库/反例 | 写这次推翻了自己什么判断 |

编号只增不减，然后更新 `20_知识库/_索引.md`。

### 第 8 步 · 讲义（用户要求时）

按 `03_知识模板.md` 的模板 B 写，存 `20_知识库/讲义_游戏名_系统名.docx`。

## 三条红线

1. **复述 ≠ 拆解**：说得出「白绿蓝紫橙」不算，要说得出「为什么是五档」
2. **必须回答「如果不这样会怎样」**：至少一次反事实推演
3. **必须写「运营一年后它会在哪崩」**：通胀 / 膨胀 / 躺平 / 付费失效 / 社交死亡，点名一种

## 常见失败与对策

| 症状 | 真实原因 | 对策 |
| --- | --- | --- |
| 参数列了十几行 | 在找数据，不在找结构 | 只留决定手感的 3~5 个 |
| 结论和开头目标对不上 | 在套模板 | 回第 1 节重写体验目标 |
| 换个游戏名读得通 | 没拆具体的东西 | 每节至少加一个该游戏独有的事实 |
| 知识卡全是理论卡 | 在搬书 | 先写经验卡，理论卡只补缺口 |
| 文档很长但没有判断 | 不敢下结论 | 第 13 节必须给出取舍 |

## 交付话术

最后一段必须包含三件事：

1. 这份拆解的命门，一句话
2. 还缺什么数据、哪些结论是猜的
3. 下一步拆哪个系统
