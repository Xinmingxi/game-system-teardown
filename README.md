# 游戏系统拆解

面向**游戏系统策划**求职的作品库。

每份拆解只干一件事：还原一个系统的设计决策——它解决什么体验问题、结构怎么搭、参数怎么调、如果不这样做会怎样、运营一年后会在哪崩。

> 复述不是拆解。说得出「白绿蓝紫橙」不算，要说得出「为什么是五档」。

## 目录

```
00_规范/     方法论、15 节模板、知识模板、工作流、进度索引
01~11/       按「核心循环相似度」分的品类，每类附 _清单.md
20_知识库/   理论卡 T- / 经验卡 E- / 反例卡 C- / 讲义 / 书单
90_横向专题/ 同一系统跨品类对比
工具/        md2docx.py（Markdown 转 Word）、autosave.ps1（定时提交）
```

## 怎么用

- 先读 `00_规范/00_总览.md`，再读 `01_拆解架构.md`
- 每份拆解产出两份同名文件：`.md` 工作稿、`.docx` 正式稿
- 转 Word：`python 工具/md2docx.py 品类\文件.md 品类\文件.docx`
- 自动保存：计划任务每 2 小时跑一次 `工具/autosave.ps1`
- 进度看 `00_规范/04_进度索引.md`

## 拆解架构（四层）

| 层 | 问的问题 |
| --- | --- |
| L1 体验 | 它想让玩家感觉到什么 |
| L2 结构 | 由哪些模块和循环组成 |
| L3 数值 | 关键参数是多少 |
| L4 表现 | 玩家看到、听到什么 |

**读的顺序从内到外，写的顺序从外到内。**

## 三条红线

1. 复述 ≠ 拆解
2. 必须回答「如果不这样会怎样」
3. 必须写「运营一年后它会在哪崩」
